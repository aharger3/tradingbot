# T64 — Execution Venues: Can OMEN Trade Options Live, and Where

## Verdict

**Robinhood can technically do this now, but not the way OMEN is built to trade.** As of August 2026 Robinhood has an official, documented Agentic Trading product built on a Model Context Protocol (MCP) server, and its own marketing page states plainly: "Now available for equities, options, and crypto." ([robinhood.com/us/en/agentic-trading](https://robinhood.com/us/en/agentic-trading/)) This is a real reversal from Robinhood's historical position (no public trading API, ToS ban on scraping/automation) and from the "Robinhood cannot do this without violating ToS" answer that would have been correct as recently as spring 2026. Robinhood's own Customer Agreement, updated July 2026, now has a full API & MCP section (§29) that says explicitly: **"External AI agents can place real trades and access your portfolio."** ([Robinhood Customer Agreement PDF](https://cdn.robinhood.com/assets/robinhood/legal/Robinhood-Customer-Agreement.pdf), §29.2)

But — and this is the part that matters for OMEN specifically — Agentic Trading is built for a *conversational* AI agent (Claude Desktop, ChatGPT, Cursor, Grok, etc.) operating inside a human-supervised session against a dedicated, separately-funded "agentic account," not for a headless cron-scheduled Python process placing dozens of tightly-timed scale-out orders. Robinhood's own risk language says the user is "responsible for monitoring your account and ensuring the agent operates as intended," that the product "may not be appropriate for all investors," and that Robinhood "is not responsible for losses resulting from agent-generated decisions." There is no evidence Robinhood publishes a plain REST/WebSocket order-entry API outside the MCP protocol — the only documented path to placing an order is through an MCP client. That is a fundamentally different integration than the REST/SDK model OMEN would need to submit a signal-to-order pipeline reliably inside a 90-minute intraday window. Treat Agentic Trading as a live open question to prototype, not as a settled "yes" — the next research step is confirming whether the MCP endpoint can be driven headlessly (no chat UI in the loop) from OMEN's existing `live_scanner.py` process, and whether options order types (multi-leg, limit, scale-out) are actually exposed yet or still rolling out.

Separately, and unconditionally: the unofficial route (`robin_stocks` et al., reverse-engineered private endpoints) remains a **ToS violation with account-termination risk**, regardless of the new Agentic Trading product. Robinhood's Terms & Conditions/customer agreements prohibit "automated searches, requests, or queries to strip, scrape, or mine data from the Services" and any "data mining, robots, or similar data gathering or extraction tools" without express written authorization — this is unchanged. Do not build on `robin_stocks`.

**Best-supported alternative for OMEN's actual shape (headless bot, options, intraday, scale-out): Tastytrade.** OMEN already authenticates against Tastytrade's real API for market data and read-only account calls (`tastytrade_feed.py`: `get_accounts`, `get_balance`, `get_positions`, DXLink quotes) — the credentialing and session-management work is already half-done. Tastytrade's [developer portal](https://developer.tastytrade.com/) documents a full read/write trading API (`developer.tastytrade.com/api-overview/`) built for exactly this kind of programmatic, headless order placement, with a sandbox at `api.cert.tastyworks.com`. Tradier is the next-best option if Tastytrade's order-placement surface turns out to be thin — it is unambiguously built for this, with free API access to every brokerage account holder and a first-class options-chain/order API.

## 1. Does Robinhood have an official API for options trading?

**Historically: no.** Robinhood's only long-standing public, documented API is the [Crypto Trading API](https://robinhood.com/us/en/support/articles/crypto-api) — "lets you view crypto market data, access your account information, and place crypto orders programmatically." It explicitly does not cover stocks or options. For years the only way to touch a Robinhood equities/options account programmatically was to reverse-engineer the mobile app's private endpoints, which is what every "Robinhood API" library (robin_stocks, sanko/Robinhood, etc.) does.

**As of 2026: this changed materially.** Robinhood launched **Agentic Trading** on May 27, 2026 ([robinhood.com/us/en/newsroom/robinhood-is-now-open-to-agents](https://robinhood.com/us/en/newsroom/robinhood-is-now-open-to-agents/)), an official product that lets AI agents place real trades through a Robinhood-hosted MCP server. At launch it supported **equities only, in beta** — the announcement said "support for options, crypto, event contracts, futures, and more are coming soon as we move out of beta." By August 2026, per Robinhood's own current marketing page, options and crypto support has shipped: "Now available for equities, options, and crypto." ([robinhood.com/us/en/agentic-trading](https://robinhood.com/us/en/agentic-trading/)) Crypto-specific expansion is also independently confirmed around August 17-19, 2026 by multiple trade press pieces (CryptoTimes, Memeburn, Crowdfund Insider) referencing the same Robinhood announcement.

Mechanically, this is **not** a conventional documented REST API with an API key you call from a script. It is:
- An MCP server URL you paste into an MCP-compatible client (Claude Desktop, Claude Code, ChatGPT, Codex, Cursor, Grok are named as supported).
- Scoped to a **dedicated "agentic account"** the user creates and funds separately from their main portfolio — the agent only ever touches money you deposit into that sub-account (up to 10 agentic accounts allowed).
- Governed by Robinhood's Customer Agreement §29 ("API & MCP"), added/updated as of the July 2026 revision, which states Robinhood retains sole discretion over who gets access ("You may not use the API Package or develop Licensee Products without Robinhood's express written consent"), that orders are subject to Robinhood's own vetting ("Robinhood cannot guarantee that any order will be accepted"), and that Robinhood disclaims liability for API/MCP latency, System Failures, and "agent-generated decisions."

**What's still unconfirmed and worth a dedicated follow-up before building against it:** whether the MCP endpoint can be driven by a non-conversational, deterministic client (i.e., can OMEN's `live_scanner.py` call it directly the way it calls Tastytrade today), what order types are actually exposed for options (single-leg only? limit only? no multi-leg spreads?), whether there's a rate limit incompatible with 60-second polling across 11 symbols, and whether options support is live for all users yet or still gated/rolling out per-account (the Finder review, updated July 1 2026, still described options as "rolling out and isn't available to everyone yet").

## 2. Unofficial libraries (robin_stocks, etc.) and the ToS

`robin_stocks` (and its many GitHub forks) is a pure-Python wrapper around Robinhood's **private, undocumented mobile-app endpoints** — it supports stocks, options, and crypto because it mimics whatever the app itself calls, not because Robinhood published or supports those endpoints for third parties. ([jmfernandes/robin_stocks](https://github.com/jmfernandes/robin_stocks))

Robinhood's own legal documents prohibit exactly this. From the Sherwood Media Terms & Conditions (Robinhood's terms wrapper): using "any data mining, robots, or similar data gathering or extraction tools to access, monitor, or copy any content or information used by the Service without express written authority" is prohibited. The Robinhood Money Spending Account Agreement carries the same restatement: no "automated searches, requests, or queries to strip, scrape, or mine data from the Services." ([cdn.robinhood.com legal documents](https://robinhood.com/us/en/about/legal/)) The July 2026 Customer Agreement's new §29.1 reinforces this directly for trading access: "You may not use the API Package or develop Licensee Products without Robinhood's express written consent (and Robinhood may decline any such request for use or development in its sole discretion)." Reverse-engineered endpoints are, by definition, used without that consent.

**Risk, stated plainly:** this is a real account-termination exposure, not a theoretical one. Multiple independent sources converge on the same practical description: Robinhood can and does close accounts it detects making automated calls outside the official app, authentication flows on the private endpoints rotate and break libraries without notice, and there is no support recourse because you are, by definition, outside any supported integration. Given Robinhood custodies real capital and Austin's account, this is not a place to cut corners even though the mechanism (Python HTTP calls) is trivial to build — the downside is total loss of brokerage access, not just a broken script.

## 4. Regulatory constraints on an intraday options bot

**Pattern Day Trader rule — being eliminated, not currently binding the way it used to be.** FINRA's historical PDT rule required $25,000 minimum equity for any account making 4+ day trades in 5 business days. The SEC approved FINRA's proposal (SR-FINRA-2025-017) to eliminate this entirely: FINRA Regulatory Notice 26-10 confirms the amendments "replace in their entirety the outdated day trading margin requirements, including the day trade count requirements for designating a customer as a 'pattern day trader' and the $25,000 pattern day trader minimum equity requirement." ([FINRA Regulatory Notice 26-10](https://www.finra.org/rules-guidance/notices/26-10); also [Federal Register, Apr 17 2026](https://www.federalregister.gov/documents/2026/04/17/2026-07485/)) Effective date: **June 4, 2026**. In its place, FINRA Rule 4210 now requires member firms to monitor for "intraday margin deficits" continuously rather than gate accounts by day-trade count — firms have until **October 20, 2027** to fully phase in the new monitoring. Practical effect for OMEN: the $25k gate that would have forced a specific account size before any 3x-a-day scalping strategy could run is gone as of this summer, replaced by an ordinary margin-sufficiency check that any properly-funded account should clear. This is recent enough (2 months old as of this writing) that it's worth re-confirming with whichever venue is chosen — broker-side implementation is still inside its 18-month phase-in window.

**Options approval levels — this still fully applies and is per-broker.** FINRA Rule 2360(b)(16) requires every options account to be specifically approved before the first order, based on the customer's stated experience, financial situation, and investment objectives — this is federal-rule-level, not just Robinhood policy. ([FINRA Rule 2360](https://www.finra.org/rules-guidance/rulebooks/finra-rules/2360)) Every venue in the table above enforces its own version of a leveled system (commonly Level 1 covered/cash-secured through Level 4 uncovered), and OMEN's break-and-retest calls/puts (simple long calls/puts, no spreads) need only the lowest tier that permits buying options outright — typically Level 2. This is a one-time account-setup step, not an engineering problem, but it has to happen before the first live order regardless of venue, and Schwab's reported month-long developer approval timeline plus the options-approval step stack sequentially.

**No specific "automated retail trading" disclosure regime exists beyond what's already covered.** There is no separate SEC/FINRA rule specifically targeting retail algorithmic/automated trading disclosure the way there is for broker-dealer market-making algos; the applicable framework is the ordinary suitability/KYC rules (Rule 2360 above) plus each broker's own API terms (Robinhood §29, or the equivalent developer agreement at Tastytrade/Tradier/IBKR/Schwab/Alpaca). The risk sits in the venue's ToS and account terms, not in a separate regulatory automated-trading filing.

## 5. The execution gap: what "long QQQ at 690.42, stop 689.56" is missing to become a real options order

OMEN's engine already goes further than raw underlying signals — `options_sizer.py` builds a full `OptionsPlan` (strike, expiration, entry/stop/target premium, contract count) from a stock-level signal, and `live_scanner.py` posts it to Discord and can paper-trade it (`paper_trader.py`). That's real, working infrastructure. But none of it submits an order to a broker. Specifically, comparing what exists today against what "execute live" requires:

**Already built (confirmed by reading the code):**
- Strike selection: `nearest_strike()` (ATM, rounded to a per-symbol increment) or `first_otm_strike()` (Scarface variant, currently off) in `options_sizer.py`.
- Expiration selection: `nearest_expiration()` (0DTE before 14:30 ET, else next trading day) or `weekly_expiration()` (nearest Friday, Scarface variant).
- Live premium quote: real-time mid from Tastytrade's DXLink feed (`tasty_feed.fetch_option_quote`), with a fallback delta-estimate (`entry_premium ≈ stock_price × 0.005`) when the feed fails — flagged in output as `quote_source: "estimated_delta"`.
- Bid/ask spread check (warns above $0.50, does not block).
- Contract sizing from max-loss budget and grade (`GRADE_SIZE_PCT`).
- Scale-out arithmetic: `paper_trader.py`'s `RULE6_SCALE_PCT` scales 50% out at breakeven and tracks a runner — but this is **simulated against candle high/low in-process**, not a resting order on any exchange.
- Read-only broker connectivity: `tastytrade_feed.py` already authenticates (OAuth) and calls `get_accounts`, `get_balance`, `get_positions` against Tastytrade's real API.

**Not built — the actual gap between a plan and a filled order:**
1. **Order submission itself.** There is no `place_order` / `submit_order` call anywhere in the repo against any broker. `tastytrade_feed.py` is read+quote-only. This is the single largest missing piece — everything else downstream assumes it exists.
2. **Order type and limit-price policy for the *entry*.** `build_options_plan` uses the live *mid* as `entry_premium`, but a real limit order needs a deliberate choice: marketable limit at mid+slippage-buffer? Peg to ask for calls/bid for puts? What tolerance before treating a fill as "didn't happen" and aborting the signal? None of this exists — the mid is currently just a number in a Discord message.
3. **Turning the stop/target into resting orders (or a monitoring loop).** Today, stop/target are premium levels compared against candle highs/lows once a minute inside `paper_trader.py`. A live version needs either broker-side stop/OCO orders (if the venue supports stop orders on options — not all do cleanly) or a monitoring loop tight enough to catch a fast move within the 60-second poll cadence, plus logic for what happens if the market gaps through the stop between polls.
4. **The 30/30/30/10 scale-out ladder as real order legs.** Current code implements one scale-out point (breakeven, 50%) as arithmetic, not as multiple limit orders at different premium levels with independent fill tracking. A real ladder needs four separate order legs (or four sequential partial closes), each needing its own fill confirmation, its own "what if this leg doesn't fill before the 11:00 flat deadline" handling, and correct remaining-contract bookkeeping.
5. **The 11:00 flat-by deadline as an enforced action.** Nothing currently force-closes a live position at 11:00 — the scan loop simply stops looking for new entries after `ENTRY_CUTOFF`. An open live position at 10:59 needs a guaranteed market-or-aggressive-limit close, not just "stop scanning."
6. **Order state reconciliation.** `paper_trader.py`'s ledger is authoritative for paper trades because nothing else is happening to those positions. A live account needs to reconcile OMEN's internal idea of "what's open" against the broker's actual position/order state — partial fills, rejects, and manual intervention (Austin closing something by hand) all have to be detected and merged back in, or the bot will act on stale state.
7. **Rejection and error handling for real orders.** Robinhood's own §29.5 spells out the general shape of this risk (orders can be rejected, latency between submission and receipt, no guarantee of acceptance) and it applies to every venue: OMEN needs explicit handling for a rejected order (bad limit, insufficient buying power, contract not tradeable, market closed for that symbol), not just for a slow/missing quote.
8. **Liquidity/tradability gating before submission, not just after quoting.** Current code has a soft "no liquidity" warning based on an empty OCC symbol; a live system needs a hard pre-trade check (open interest, volume, spread ceiling) that blocks submission outright, since a bad fill on a real order costs real money in a way a Discord warning does not.
9. **A kill switch independent of the signal loop.** The scan loop already halts on consecutive losses / daily trade cap / regime filter — all of that is signal-generation logic. Live trading additionally needs an operator-controlled circuit breaker (manual and automatic, e.g., broker API errors spiking, account equity dropping past a threshold) that can freeze order submission without needing to kill the whole process.
10. **Credential/session hardening for a second broker relationship (if the venue differs from Tastytrade).** `tastytrade_feed.py`'s OAuth flow is built for data/read calls; a trading-capable credential is a materially higher-value secret (per OMEN's own security note about `POLYGON_API_KEY` leaking into tracebacks) and needs the same discipline applied to whatever token authorizes order placement.

None of this is exotic — it's the standard shape of "signal engine" to "execution engine," and Tastytrade's existing connection in this repo means most of items 1-4 above are a matter of adding write-API calls to an already-authenticated client, not building broker integration from zero. But it is a real body of engineering, testing, and paper-validation work, not a config flag.
